## Outcome

The next release can evolve the schema without invalidating established v1.0.0 CLI and Cue JSON workflows.

## Context

Current schema plumbing compiles one embedded exact version, and the model recognizes only SubRip and WebVTT with fixed stable capabilities. Changing a version constant alone would not demonstrate backward compatibility.

## Scope

Define exact supported input identities, historical schema selection, semantic validation by contract version, producer-version independence, new-output identity, capability states, and error behavior. Keep released schema copies immutable and preserve existing CLI behavior.

## Acceptance criteria

- [ ] A version/command matrix covers v1.0.0 inputs on the new executable and unchanged old supported workflows, streams, codes, loss behavior, and restoration.
- [ ] Historical document identity and producer provenance are not silently rewritten during validation, inspection, rendering, conversion, or restoration.
- [ ] Unknown, mismatched, and unsupported schema identities fail explicitly; no broad semver acceptance or network schema retrieval is introduced.
- [ ] New native encoding uses the current output contract; historical validation uses its exact immutable contract and version-specific semantic rules.
- [ ] Both current v1.0.0 and planned v1.1.0 reject v0.0.0 input identity; the historical v0.0.0 executable remains available, and no extra adapter promise is invented.
- [ ] Executable/current emitted schema lockstep remains required, while historical input support is a separate capability; any unavoidable break forces a major-version decision.

## Dependencies

Native blockers: [#52](https://github.com/shruggietech/cueson/issues/52). Coordination across the same implementation slice does not add reciprocal dependencies. Protected release/tag and production transitions require their own explicit operator authority.
